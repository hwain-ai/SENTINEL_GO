# go-mutesting 실험 연결

SENTINEL이 자체 변이 규칙을 복사하지 않고 외부 go-mutesting 라이브러리의 함수를 직접 호출하도록 연결했다. 아직 공식 검사 통과를 발행하는 기본 backend는 아니다. 기존 mutate4go 명령과 잠금 파일은 유지한다.

변이는 테스트가 오류를 잡는지 확인하려고 일부러 바꾼 코드다. adapter는 외부 도구를 SENTINEL의 실행·결과 형식에 연결하는 코드다.

## 버전과 범위

- 외부 module은 github.com/avito-tech/go-mutesting, 버전은 v0.0.0-20251226130216-48d0401f00fb다. [go.mod](../go.mod)와 [go.sum](../go.sum)으로 버전과 다운로드 내용을 고정한다.
- expression/comparison, numbers/decrementer, numbers/incrementer 함수를 외부 package에서 직접 가져온다. 변경 규칙 본문은 복사하지 않는다.
- profile은 comparison-and-numbers-v1이다. 세 규칙으로 생성한 후보 전체를 처리한다는 뜻이며, 외부 도구의 전체 규칙 지원을 뜻하지 않는다.
- 명시한 module-relative Go 소스만 처리한다. 테스트 파일, 중복·상위 경로, 잘못된 구문은 거부한다. 후보 ID에는 원본·변경 내용 지문과 물리적 위치가 들어간다.
- 읽기는 소스당 4 MiB와 초과 확인용 1 byte로 제한한다. 변이 소스 합계는 최대 32 MiB이며 초과하면 전체 요청을 거부한다. 원본 프로젝트 전체 복사량은 아직 별도 상한이 없다.
- MIT 고지는 [제3자 라이선스](../third-party-notices/go-mutesting-LICENSE.txt)에 보관한다. probe 바이너리를 배포할 때 함께 제공해야 한다.

외부 API와 구현 상태를 다루므로 한 달 뒤 다시 확인한다. 버전 갱신 시 세 함수의 제공 여부, 후보 ID와 재실행 결과를 검증한다.

## 처리 순서

1. 원본 파일 목록·내용 지문을 기록하고 임시 복사본을 만든다. 기존 workspace 규칙에 따라 링크·안전하지 않은 파일을 거부한다.
2. 외부 함수로 전체 변이 후보를 먼저 확정한다. 규칙 적용·복원은 복사본에서 만든 구문 트리에서만 일어난다.
3. 원본 상태를 새 복사본 두 개에서 각각 테스트한다. 둘 다 정상 통과해야 진행한다.
4. 후보마다 새 복사본 두 개에서 테스트한다. 단정문 실패·실행 중 오류·컴파일 오류를 구분하고, 원본과 동일한 테스트 선언 목록인지 확인한다. 두 재실행의 소스·실제 테스트 결과·실패한 검사 위치 지문도 정확히 비교한다.
5. 테스트 파일을 복원하기 전에 설치한 계측 내용이 그대로인지 확인한다. 복원 후에는 원본과 복사본 전체의 변경 여부를 확인하고 임시 복사본을 정리한다. 오류 시 결과를 발행하지 않는다. 관찰에 성공해도 certified는 false다.

비공개 이벤트 통로는 총 16 MiB로 제한하고 취소 시 대기를 중단한다. 테스트 명령은 별도 프로세스 그룹에서 실행하며 같은 그룹 자식을 함께 종료한다. 별도 세션으로 이탈한 자식까지 가두는 OS 보안 격리는 구현하지 않았다. 신뢰할 수 있는 프로젝트에서만 사용한다.

## 사용법

고정 Go 1.27.1이 준비된 저장소에서 [scripts/go.sh](../scripts/go.sh)로 별도 probe를 빌드한다. build는 실행 파일 생성, -trimpath는 빌드 경로 제거, -o는 출력 파일 지정이다. 예시 출력 경로가 이미 쓰이는 환경에서는 다른 임시 경로를 선택한다.

```bash
# scripts/go.sh: 고정 Go 실행기, --offline: 네트워크 다운로드 금지.
# build: 빌드, -trimpath: 빌드 경로 제거, -o: 출력 파일 지정.
# 마지막 ./cmd/...: 빌드할 별도 실험 명령의 소스 폴더.
scripts/go.sh --offline build -trimpath -o /tmp/sentinel-go-mutesting-probe ./cmd/sentinel-go-mutesting-probe
```

생성한 명령의 --help로 인자를 확인한다. --project는 검사할 module, --source는 그 안의 파일이며 반복 가능하다. --go-binary에는 이 저장소의 .toolchain/go-1.27.1/bin/go 절대 경로를 전달한다. --timeout-ms는 원본 대조와 모든 후보 실행이 공유하는 전체 제한 시간이며 기본 60초, 최대 1시간이다.

선택 인자 --mutant-timeout-ms는 각 후보의 개별 재실행에 1~3,600,000 ms의 상한을 적용한다. 두 재실행이 하나의 제한을 나누는 방식이 아니다. 이 인자를 생략하면 각 재실행은 기존처럼 남은 전체 시간만 적용받는다. 명시한 값은 --timeout-ms보다 클 수 없으며, 원본 대조 재실행은 이 짧은 상한을 적용받지 않는다. 이 실행 옵션은 planSha256에 포함되지 않으며, planSha256은 후보 발견을 묶는 식별값이지 실행 인증이나 admission 증거가 아니다.

파일 복사·후보 생성·검증·정리는 중간에 즉시 취소되지 않는다. 제한 시간이 전체 작업의 실제 종료 시각을 보장한다는 뜻은 아니다. 제한을 넘긴 결과는 성공으로 발행하지 않는다.

JSON은 표준 출력에만 쓴다. 원본·변이 코드, 원본 절대 경로, 원시 테스트 출력은 포함하지 않는다. .sentinel 증거·이력은 만들지 않는다.

## 반복 검사에서 비교하는 값

지문은 내용을 SHA-256으로 계산한 식별값이다. 지문이 같다는 것은 기록한 입력이 같다는 뜻이며, 프로그램의 모든 실패 원인이나 보안 격리를 증명한다는 뜻은 아니다.

| 출력 항목 | 실제로 묶이는 내용 |
|---|---|
| projectSha256 | 복사 대상 전체 파일의 상대 경로와 내용. 테스트·go.mod·데이터 파일 포함. .git·.sentinel·.toolchain·target은 기존 복사 정책대로 제외 |
| planSha256 | 도구 버전·제한 profile·프로젝트 지문·명시한 소스 목록·전체 후보 목록. 후보가 0개인 파일도 포함 |
| control | 서로 다른 원본 복사본에서 실행한 두 대조 기록 |
| replays | 후보 ID와 첫째·둘째 실행의 기록 |
| 각 실행의 inputSha256 | 실제로 실행한 복사본 내용. 두 원본 대조는 프로젝트 지문과 같고, 같은 후보의 두 실행은 서로 같아야 함. 원본·변이 지문의 차이도 출력에서 확인 가능 |
| inventorySha256 | 실행 전에 확보한 테스트 선언 이름·종류의 전체 목록 |
| resultsSha256 | 실제 실행된 테스트·하위 테스트의 시작과 종료 상태. 병렬 도착 순서는 무시하되 반복 횟수는 보존 |
| failureSha256 | 실패 테스트·하위 테스트와 기록된 직접 실패 호출 위치·횟수. 검출로 분류할 때 필수 |

실패 위치는 테스트 소스 내용 지문, 파일·package, 물리적 위치, 호출 이름에 연결한다. Fail·FailNow·Error·Errorf·Fatal·Fatalf를 직접 호출하는 testing.T·testing.F·testing.TB 매개변수를 지원한다. 같은 이름의 다른 지역 변수는 검사 대상으로 오인하지 않는다. 예제 출력 불일치는 예제 식별자와 프로젝트 입력 지문에 묶는다. [기록 코드](../internal/runner/assertion.go)

지원하지 않는 호출 방식, 예를 들어 실패 메서드를 변수에 넣어 호출해서 실패 위치를 얻지 못한 경우에는 검출 성공으로 세지 않는다. 외부 assertion 라이브러리 전체나 기록하지 못한 추가 실패까지 지원한다는 뜻은 아니다. 벤치마크·사용자 TestMain·같은 폴더의 혼합 테스트 package 등 기존 실행기의 지원 제한도 유지한다.

실패 호출을 기록할 때 원래 인수 목록을 유지하고 이름 있는 메서드로 연결한다. 여러 값을 한 번에 반환하는 인수, 지연 실행되는 실패 호출, Go의 vet 검사에서 거부하는 잘못된 형식 문자열을 회귀 테스트로 대조했다. 테스트 없는 보조 폴더에는 TestMain을 추가하지 않으며, 실행할 테스트와 같은 package의 보조 파일은 실패 위치 기록에 포함한다.

이 기록은 probe에만 노출한다. 일반 typed runner의 v1 JSON 출력과 기본 backend는 변경하지 않는다. 실행마다 새 nonce를 발급하고, 같은 nonce·다른 소스·다른 목록·다른 검사 위치를 재실행 증거로 받아들이지 않는다. [결합 검사](../internal/gomutesting/run.go)

복원은 일반 typed runner에도 적용되는 보호다. 테스트가 계측 파일을 바꾼 경우 먼저 오류로 처리하며, 심볼릭 링크·하드 링크·바뀐 부모 경로를 따라 복원하지 않는다. 예상하지 않은 일반 파일 편집도 덮어쓰지 않는다. 검사 사이에 바꿨다가 되돌린 내용이나 실행 중인 외부 프로세스와의 모든 경로 경쟁을 탐지하는 보안 격리는 아니다. [복원 코드](../internal/runner/restore.go), [파일 보호 테스트](../internal/runner/restore_test.go)

## 검증과 남은 조건

작은 Positive 함수의 강한 테스트는 변이 3개 검출, 입력 1만 확인하는 약한 테스트는 1개 검출·2개 생존이었다. 잘못된 결과에서 panic을 내는 테스트는 3개 모두 runtimeError이며 killed로 올리지 않았다. 배열 크기 변이의 컴파일 오류도 별도로 분류했다. [실행 테스트](../internal/gomutesting/run_test.go)

원본 변경 탐지, 시간 초과, 0개 후보, 입력 거부, 출력의 소스 비노출과 종료 6을 검사한다. 같은 그룹 자식이 제한 시간 뒤 파일을 쓰는 결함은 재현 후 수정했다. 열린 이벤트 통로의 취소와 과다 입력 거부도 회귀 테스트에 포함한다. [실행기 테스트](../internal/runner/process_test.go)

2026-09-08 최종 전체 Go 패키지 테스트와 연결·명령·실행기·복사본의 race 검사(동시 실행 오류 검사)가 통과했다. 연결의 plan.go·run.go·identity.go, probe의 main.go, 실행기의 execute.go·instrument.go·assertion.go·replay.go·restore.go, 복사본의 digest.go에서 함수 124개를 실제 coverage로 측정해 CRAP 기준 초과 0개·측정 불가 0개를 확인했다. 전체 저장소나 생성된 테스트 helper까지 CRAP 승인을 받았다는 뜻은 아니다. module 무결성 검사도 통과했다.

독립 검토에서 찾은 다중 반환 인수의 컴파일 실패, 보조 폴더의 잘못된 계측, 복원에 가려지는 테스트 파일 변경, vet 검사 우회를 실패 테스트로 재현한 뒤 수정했다. 링크 대상과 예상하지 않은 편집을 보존하는 테스트도 추가했다. 검토자가 수정 후 관련 테스트를 다시 실행해 남은 중요 문제를 발견하지 못했다. 실제 probe의 약한 테스트 실행은 1개 검출·2개 생존, 원본 대조 2개·후보 재실행 쌍 3개, certified=false, 종료 코드 6이었다.

공식 도입 순서는 다음과 같다.

1. 이번에 추가한 목록·소스·실패 위치 결합을 실제 프로젝트에서 검증한다. 직접 호출 범위 밖의 assertion, 외부 상태 변화, 실행기 자체 무결성·서명까지 검증한 인증 증거로 오해하지 않는다.
2. 더 넓은 규칙 범위, 실행되지 않은 변이 구분, 지원하지 않는 언어 요소를 검증한다. 제한 profile을 전체 검사로 표시하지 않는다.
3. 실제 프로젝트에서 기존·신규 도구의 범위·검출·시간을 비교하고 복사 비용·자원 상한을 측정한다.
4. 운영 격리와 완전한 증거 결합을 승인한 뒤 기본값 전환을 별도로 결정한다. 그때까지 probe 사용을 중단해도 기존 명령의 결과 의미는 바뀌지 않는다.
