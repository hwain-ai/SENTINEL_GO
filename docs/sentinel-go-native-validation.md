# Go 독립 설치·실제 프로젝트 검증

Go의 독립 설치·격리 실행 기반을 구현했고 공개 프로젝트의 원래 빌드와 두 도구의 전체 생산 파일 비교 기록을 검토했다. 새 10파일 비교용 설치물에서는 원래 빌드에 이어 격리 시험 10종과 각 시험 뒤 새 실행의 복구도 확인했다. 이어서 설치된 통합 명령에서 같은 공개 프로젝트 복사본의 검사 결과 반환·제한 실행·사용자 취소를 확인했다. 이 검증은 프로젝트의 품질 통과를 뜻하지 않는다. 정식 운영 허용, 다른 언어 검증과 Codex·Claude Code 플러그인 활성화는 아직 미완료다. 단계별 설치물과 검증 범위는 아래에서 구분한다.

이 문서는 [실행 계획의 Task 2c·2d](https://github.com/hwain-ai/SENTINEL/blob/main/docs/exec-plans/active/2026-09-sentinel-unified-entry.md)에 대한 관측 기록이다. 공개 참조 프로젝트 하나를 회사 프로젝트 전체의 대표로 취급하지 않는다. 모든 실행 결과는 certified=false다.

## 입력과 설치 범위

- 프로젝트: HashiCorp go-multierror v1.1.1, commit 9974e9ec57696378079ecc3accd3d6f29401b3a0. Git을 제외한 20개 파일, 43,724 bytes를 고정했다. go.mod의 Go 1.13 선언과 원본 테스트를 유지했다.
- runtime: 기존 잠금의 Go 1.27.1 Linux amd64. 전체 15,639개 파일, 243,910,739 bytes를 검증했다. 원래 release 권한으로 계산한 GNU tar 지문을 유지하면서 설치 파일은 읽기 전용으로 봉인한다.
- dependency: errwrap v1.0.0의 별도 module cache. 다운로드를 끈 상태로 무결성을 확인한다.
- artifact: sentinel-go, typed test runner, mutate4go bridge의 3개 실행 파일과 make·go-mutesting probe·라이선스·기록을 합친 9개 파일이다. SDK·프로젝트·module cache와 별도 주소로 설치한다.

수정 artifact는 서로 다른 출력·build cache에서 두 번 빌드해 4개 Go 실행 파일의 SHA가 각각 같음을 확인했다. make와 라이선스는 바꾸지 않았다. source manifest는 122개 파일이며 SHA는 77930f7cb772fa146f286f136457051d2d599cf87c28ddcfc02e50e043771b2b다. 이전 artifact는 덮어쓰지 않았다.

후속 v4도 새 출력·독립 build cache 두 곳에서 빌드해 4개 실행 파일의 지문 일치를 확인했다. 빌드 전후 124개 source manifest SHA는 0eae0d7754379b7e61ddd902cf2b91a22fe7f39ef171563151313ffd5793facf로 같았다. SDK·module cache·corpus와 이전 artifact는 바꾸지 않고 새 artifact만 추가했다. 진행 중인 mutate4go 회수 보완은 이 v4에 포함하지 않았다.

후속 v5는 mutate4go 회수·출력·시간 제한 보완의 독립 승인 뒤 만들었다. 독립 빌드 두 곳의 실행 파일 4개가 일치했으며, 빌드 전후 132개 source manifest SHA는 af3844dbe416a0be7e231c827cb5a7b09855d2db90b55c5f7f67c0185ffeda8a로 같았다. 새 artifact는 9파일/25,491,485 bytes다. 기존 v4와 SDK·module cache·corpus·잠금 파일은 보존했다.

첫 5개 실행 모두 host의 네 설치 root를 다시 검증했고, 컨테이너 내부에서 작업 복사본의 전후 입력 지문 일치와 컨테이너 제거를 관측했다. 마지막 mutate4go 실행 이후 전체 ownership label 조회도 0개였다.

sort.go의 go-mutesting 관측은 comparison-and-numbers-v1 프로필이며 전체 upstream 변이 규칙을 사용한 결과가 아니다. 원본 테스트 두 번과 변이 적용 후 테스트 두 번에서 실행별 식별값은 달랐고 테스트 목록 지문은 같았다. 두 변이 실행 모두 통과했으므로 survived, 즉 해당 변경을 테스트가 잡아내지 못한 것으로 기록했다. 입력 파일 지문은 03c65ab4421ad866919b30e14e386c4fc55812a7208794eb46f3012e9ebd3006이다. 이 한 건만으로 mutate4go와의 우열이나 전체 프로젝트 점수를 계산하지 않는다.

초기 private 비교 스크립트의 종료 판정에는 별도 문제가 있었다. 병렬 실행 중 다른 실행의 컨테이너가 남아 있다는 이유로 doctor/comparison 스크립트가 종료 1을 냈고, 짧은 Docker ID도 64자리와 혼동했다. 각 작업의 정확한 ID 제거 확인과 모든 작업 종료 뒤 전체 부재 확인을 분리하고 --no-trunc를 적용했다. native 종료 값과 검증 스크립트 종료 값을 혼동하지 않는다.

전체 7파일 재실행 중 실제 대기 중인 테스트 프로세스의 작업 복사본을 읽기 전용으로 대조했다. group.go의 WaitGroup.Add(1)이 Add(2)로 바뀌었고 완료 처리는 한 번인 상태였다. 테스트 실행 인자는 -test.timeout=10m0s였다. 이 관측은 현재 go-mutesting 실행의 무한 대기 원인을 설명하지만, 앞선 mutate4go 시간 초과의 원인까지 증명하지는 않는다. 실행 후 네 입력 root와 작업 복사본의 보존, 정확한 컨테이너 제거, 전체 소유 컨테이너 0개를 확인했다. 개별 변이 제한과 전체 비교 제한을 분리하는 수정은 별도로 검증 중이다.

v4 첫 실행은 도구 출력 전에 sandboxFailed로 중단됐다. 정확한 고정 image ID를 읽기 전용으로 조회하니 로컬 이미지가 없었고 소유 컨테이너는 0개였다. 같은 승인 digest를 다시 받아 image identity와 별도 복구 실행을 검증한 뒤 새 인스턴스에서 위 make·doctor를 실행했다. 이미지가 사라진 원인은 확인하지 못했으며, 버전 변경이나 실행 제한 완화는 하지 않았다. 두 정상 실행 종료 뒤에도 소유 컨테이너는 각각 0개였다.

v4 전체 비교의 상태 분포는 killed 7개, survived 8개, timedOut 1개, compileError 6개, runtimeError 7개다. 나머지 상태는 모두 0개이며 합계는 29개다. 이 결과도 comparison-and-numbers-v1의 비교·숫자 변이 규칙에 한정한다. 전체 생산 파일을 사용했다는 뜻이지 upstream의 모든 변이 규칙을 사용했다는 뜻은 아니다.

원본 control 2회와 변이 재실행 58회의 식별값은 모두 달랐고 테스트 목록 지문은 같았다. 각 후보의 두 실행 결과와 입력 지문이 일치했으며 killed 7개에는 assertionFailure의 실패 지문이 있었다. 시간 초과 후보는 이번 v4에서는 multierror.go 110행의 numbers/decrementer였고, 이후 후보 6개도 모두 결과가 남았다. 이전 v3에서 관측한 group.go 대기와 같은 사건으로 표시하지 않는다. 전체 native stdout 31,968 bytes를 잘림 없이 지문 대조해 저장했고, 입력 보존·timeout/OOM 없음·컨테이너 회수·최종 소유 컨테이너 0개를 확인했다. 두 backend 비교와 위조 방지 admission은 여전히 미완료다.

v5 mutate4go 요약은 killed 13개, survived 5개, uncovered 2개, timedOut 1개, runtimeError 12개이며 나머지 상태는 0개다. 서로 다른 후보 식별값 33개와 범위·합계가 일치했고 제외는 0개다. 시간 초과는 28번째 요약에 있고 이후 5개 요약도 남았다. native stdout 3,931 bytes의 SHA는 ede0bc97f6a31349371f59a3dbfec216afda7870ea0ea416c917ed0e053e09bc다. 원래 빌드·진단·변이 세 실행 모두 입력 불변과 정확한 컨테이너 회수를 확인했으며, v5부터는 최종 빈 컨테이너 목록도 관측 파일 지문과 함께 별도 완료 기록에 저장했다.

중요한 한계: mutate4go의 현재 공개 보고서는 후보 식별값·상태만 남기고 원본 대조·변이 재실행의 상세 기록과 테스트 목록 지문은 남기지 않는다. 따라서 위 숫자를 go-mutesting 29개와 일대일 비교하거나, 두 도구가 같은 테스트를 실행했다고 증명하거나, 시간 초과의 소스 위치를 지정하지 않는다. 두 도구의 변이 규칙도 다르므로 검출 수만으로 우열을 정하지 않는다. v5 실제 기록의 독립 검토는 완료했지만 상세 실행 증거 보존은 후속 단계다.

## 재현 후 수정한 부분

1. 테스트에 덧붙이는 assertion helper가 Go 1.18부터 제공되는 any를 사용했다. Go 1.13·1.17 선언의 통과/실패 테스트 4가지가 모두 compileError가 되는 것을 확인했다. 생성되는 helper만 interface{}로 바꾼 뒤 4가지가 의도한 passed/assertionFailure로 처리됐고 원본 go.mod·테스트 내용도 유지됐다. 외부 변이 규칙과 backend 버전은 바꾸지 않았다. 근거: [Go 1.18 언어 변경](https://go.dev/doc/go1.18), [helper](../internal/runner/assertion.go), [회귀 테스트](../internal/runner/replay_test.go).
2. artifact 기록을 읽은 실제 byte의 크기·SHA를 설치 목록과 직접 대조한다. 읽는 순간 파일을 바꿨다가 복원하는 재현을 거부한다.
3. runtime 객체에 원본 lock byte를 보존하고 입력 조립·재검사마다 정확한 내용과 SHA를 확인한다. runtime과 artifact에 같은 가짜 lock SHA를 넣는 경우도 거부한다.
4. 깊은 JSON은 최대 64단계를 적용하고 파서의 재귀 초과도 고정 오류로 처리한다. traceback을 공용 결과로 내보내지 않는다.
5. Go의 초기·최종 입력 검사까지 취소 처리 범위에 포함했다. 실제 입력 지문 계산 중 SIGINT가 일반 입력 오류로 바뀌던 경우를 재현했고, 내용 검사 본체의 취소를 Go 실행기까지 전달하도록 수정했다. 승인된 공용 content root API의 오류 계약은 유지한다.
6. signal handler, 즉 중단 신호를 처리하는 함수의 복원 중 취소와 기존 회수 실패가 겹치면 실패 6을 보존한다. 취소는 별도 상태로 유지하며 다음 실행을 시작하지 않는다. 정상 결과에 늦은 취소만 있으면 취소 8이다. 원래 처리기의 복원도 회귀 시험으로 확인했다.
7. 직접 내용 검사를 호출하면서 빠졌던 OS 경로 오류 변환을 추가했다. 실제 설치 root를 검사 도중 이동한 후속 재현은 goRuntimeFailed/5로 끝났고 절대 경로를 노출하지 않았다. 실제 SIGINT 전달과 열린 파일 연결 수의 복원도 유지됐다.
8. Go 실행 제한이 끝난 뒤 같은 만료된 context로 이벤트를 수집하면 typed timedOut 대신 수집 오류가 되는 결함을 합성 시험에서 20회 모두 재현했다. 실행 종료 후에는 호출자 context 아래에서 최대 1초만 별도로 수집하고, 호출자의 취소·전체 제한 초과는 오류로 유지하도록 수정했다. go test에는 -timeout=0을 명시해 숨은 10분 panic 제한을 제거했지만, 유효한 모든 요청에는 기존의 유한한 외부 실행 제한이 그대로 있다. 따라서 10분보다 긴 요청은 이제 명시한 외부 제한을 따른다. 복원 뒤 최종 취소 확인과 복원 오류 우선순위도 검증했으며, 이 하위 수정은 독립 v3 검토에서 승인됐다. 이후 v4 artifact의 원래 빌드·진단 결과는 위에 따로 기록했다.
9. timeout과 출력 초과가 겹치는 실제 child 회귀 시험에서, 오류 확인 순서뿐 아니라 bytes.Buffer의 ReadFrom 메서드가 제한용 Write를 우회하는 문제도 확인했다. 출력 연결에는 Write만 노출하고 출력 초과를 timeout보다 먼저 검사하도록 보완했다. 정상 종료·timeout 두 경로에서 16 MiB 초과 출력을 오류로 거부하며 원본과 프로세스 회수를 확인했다. 이후 root의 캐시 없는 Go 전체 테스트는 종료 0이었고 테스트가 있는 13개 패키지가 통과했다. 독립 v3 검토의 잔여 Critical·Important·Minor는 모두 0개다. 기존 artifact를 새 수정본으로 표시하지 않는다. mutate4go adapter의 같은 형태는 별도 후속 범위로 기록했고 여기서 수정하지 않았다.
10. go-mutesting에 선택형 개별 변이 실행 제한을 추가했다. 생략하면 기존 동작을 유지하고, 지정하면 변이 적용 후 각 재실행에만 제한을 적용한다. 원본 control 테스트는 전체 실행 시간을 사용할 수 있다. 전체 제한·취소 때는 부분 보고서를 폐기한다. 합성 프로젝트에서 멈춘 변이를 timedOut으로 남긴 뒤 다음 후보를 계속 처리하고 원본을 보존하는 시험을 통과했다. API·명령 인자·오류 우선순위까지 독립 승인됐고 root의 새 Go 전체 시험에서 13개 테스트 패키지가 통과했다.
11. 설치된 통합 실행기의 내부 comparison 요청에도 이 선택값을 연결했다. 정수 1..840000만 해당 lane에서 허용하고 잘못된 값은 Docker 호출 전에 거부한다. 생략하면 이전 artifact에도 새 옵션을 전달하지 않는다. 관련 27개 시험과 전체 223개 시험이 통과했고, 설치된 14개 source 파일의 byte 일치와 설치본 전용 6개 시험도 확인했다. 독립 검토의 잔여 Critical·Important·Minor는 0개다. 공용 CLI 옵션·격리 자원·backend 기본값은 바꾸지 않았다.
12. mutate4go adapter·bridge·typed runner의 취소와 회수 경계를 보완했다. 직접 자식의 종료 대기를 마치고 자기 프로세스 그룹에 종료 신호를 보낸 뒤 반환한다. 원래 오류와 작업 복사본 제거 실패가 겹치면 두 분류를 경로 노출 없이 보존한다. 출력 제한 우회와 취소·실패 시 정리도 회귀 시험·독립 검토를 통과했다. 직접 자식이 아닌 모든 후손의 종료 대기까지 수행한다고 주장하지 않는다.
13. mutate4go에도 선택형 변이 제한을 연결했다. 생략한 기존 호출은 유지하고, 지정하면 각 컴파일과 각 재실행에 독립 적용한다. 원본 대조 테스트와 전체 제한은 유지하며 취소·전체 시간 초과 때는 미완성 결과를 버린다. native 본체 13개와 bridge 쪽 6개 테스트 패키지의 새 전체 실행이 통과했고 독립 검토 잔여 항목은 0개다. 통합 실행기의 mutation·check 내부 연결은 정수 1..600000을 Docker 실행 전에 검증한다. 관련 29개·전체 230개 소스 시험, 재설치 14파일 byte 일치와 설치본 native·comparison 연결 시험 12개를 통과했고 독립 승인됐다. 위 v5 실제 실행은 이 설치본을 사용했다.

입력 검증 수정은 수정 전 6개 실패를 확인한 뒤 관련 8개 테스트가 통과했다. 별도 후속 검토도 실제 SDK·9파일 artifact에서 이전 재현의 거부, 정상 입력의 통과와 FD 누수 0을 확인해 ACCEPT했다. [runtime 검증](https://github.com/hwain-ai/SENTINEL/blob/main/src/sentinel/go_runtime.py), [입력 조립](https://github.com/hwain-ai/SENTINEL/blob/main/src/sentinel/go_inputs.py).

## 격리와 검증의 한계

네 입력만 읽기 전용으로 연결하며 원본 Git 저장소와 Docker socket은 보이지 않는다. UID/GID 1000, CPU 2, 메모리 2 GiB, 추가 swap 0, PID 128, 열린 파일 1,024개가 고정되어 있다. 작업 project 128 MiB, 출력 임시 영역 128 MiB, Go 실행·빌드 state 1 GiB는 실행마다 새 tmpfs다. 네트워크와 외부 다운로드를 끄고 실제 create/inspect 값을 대조한다.

아래 격리 기반 검증 시점의 통합 실행기 전체 216개 테스트는 10.962초에 통과했다. Python 3.9.25의 copy-mode 재설치 후 설치본과 source를 재귀 대조해 차이가 없었다. runtime/input 취소 후속 검토와 Go/common lifecycle 후속 검토는 모두 ACCEPT이며 해당 범위의 Critical·Important·Minor 잔여 지적은 없다. 이후 comparison 연결 수정의 전체 시험은 223개/10.862초다. 최신 v4에서 아래 모든 실제 실패 시험을 다시 수행했다고 의미를 넓히지 않는다.

Go mount 프로필에서 다음 10종을 실제 설치본으로 실행했다. 자원 제한을 검사한 컨테이너 안의 전용 실패 fixture이며, 실제 프로젝트 품질 시험으로 세지 않는다. 각 시험 뒤 host의 네 입력 root를 재검사하고 새 GoSandbox의 help 실행이 종료 0, 입력 지문 일치, 컨테이너 제거로 끝나는 것을 확인했다.

|시험|관측|
|---|---|
|기본 설정|UID 1000, 열린 파일 1,024개, 고정 cgroup 제한, host·socket·부모 환경 비노출, 읽기 전용 입력, network none, 권한 제한 확인|
|시간 초과|8초 제한으로 중단, timed_out=true, native 결과는 없음, 정확한 컨테이너 제거|
|별도 session 자식|setsid로 분리된 자식이 있어도 제한 안에 컨테이너 종료·제거|
|CPU|cgroup의 제한 적용 횟수 증가|
|PID|프로세스 개수 제한 도달 기록 증가|
|초기 입력 검사 중 취소|실제 SIGINT 후 sandboxCancelled/8, 취소 상태 유지, 원래 신호 처리기 복원|
|최종 입력 검사 중 취소|실제 SIGINT 후 sandboxCancelled/8, 취소 상태 유지, 원래 신호 처리기 복원|
|실행 중 취소|실제 SIGINT 후 sandboxCancelled/8, 컨테이너 제거, 취소된 인스턴스의 재실행 거부|
|메모리 부족|oom_killed=true. bootstrap 종료 값이 0이어도 native 결과와 내부 입력 보존을 인정하지 않음|
|출력 저장 공간 초과|128 MiB에서 쓰기 실패, native 종료 2. 호스트로 수집한 출력은 65,914 bytes이며 컨테이너 제거|

초기·최종 검사와 실행 중 취소, 메모리·출력 시험은 내용 검사의 SIGINT 전달 수정 후 설치본에서 수행했다. 마지막 OSError 수정은 관련 실제 경로 이동·SIGINT 재현, 전체 216개 테스트와 재설치 대조로 검증했다. 그 수정 전에 완료된 정상 실행을 마지막 빌드로 재실행했다고 표시하지 않는다.

공통 no-host-mount 프로필도 signal guard 수정 후 기본 설정·취소·timeout을 다시 시험했고, 이어 image 준비·별도 session 자식·OOM·PID·CPU·출력 초과와 각 후속 복구를 재확인했다. 두 프로필의 모든 실행이 끝난 뒤 ownership label 조회는 정확히 빈 출력, 컨테이너 0개였다. 이 결과는 강제 프로세스 사망의 모든 시점이나 임의 언어·빌드 조합까지 검증했다는 뜻이 아니다.

RISK(security/evidence): host의 설치 root는 host에서 다시 확인하지만, 컨테이너 내부의 작업 복사본 검사와 도구 종료 관측은 같은 UID의 bootstrap·프로젝트 실행 경계 안에 있다. 악의적인 프로젝트에 대해 위조 불가능한 품질 증거라고 주장하지 않는다. 현재 GoRunObservation은 실험 관측이며 strict admission·공용 pass 결과에 연결하지 않는다. 신뢰된 Docker daemon과 host kernel의 모든 취약점을 차단하는 VM 보장도 아니다.

## 별도 비교용 실행기 검증

원본 입력과 각 테스트 실행을 구분해 기록하는 별도 명령 sentinel-go-reference-runner를 추가했다. 기존 runner의 입력·테스트 목록·실행 결과·실패 위치 지문 계산을 재사용하며, 호출자가 정한 요청 식별값과 실제 실행기가 새로 만든 식별값을 함께 남긴다. 기존 typed runner 명령·변이 규칙·고정 버전은 바꾸지 않았다. [새 실행기의 계약과 한계](../docs/go-reference-execution.md)에 상세 범위를 기록했다.

작업 복사본 준비 중 취소, 취소와 정리 실패의 동시 발생, 테스트 실패 시 자식 정리를 재현해 보완했다. 수정본의 새 전체 Go 시험에서 테스트 패키지 15개가 통과했고, 별도로 만든 개발용 실행 파일의 명령 시험 2개도 통과했다. 독립 검토는 Approved/Critical 0/Important 0/Minor 0이다. 기존 v5 source 132개 파일이 변하지 않았음을 별도로 확인했다.

이 명령은 비교 전용이며 certified=false다. 상세 실패 위치를 수집할 수 없는 경우 toolError와 비어 있는 replay를 그대로 남긴다. 기존 명령과 분류가 달라질 수 있으므로 과거 v4/v5 결과를 소급해 보강한 것으로 세지 않는다. 작은 합성 프로젝트 시험을 마쳤다는 뜻이지, 이 실행기의 정식 설치·실제 프로젝트 비교·운영 승인까지 완료했다는 뜻은 아니다. 이후 아래 작업에서 bridge, 즉 mutate4go와 실행기를 잇는 코드에 실제 호출과 기록 검사를 연결했다.

## 비교 기록 연결 검증

mutate4go bridge에 두 옵션을 함께 지정할 때만 동작하는 비교 경로를 추가했다. 원본 실행 2회와 각 변이 재실행 2회의 실제 기록을 받아 요청·원본·테스트 목록·결과 지문을 대조한다. 컴파일 실패와 시간 초과에는 실행하지 않은 단계를 명시하고, 검사 대상에서 빠지거나 오류가 난 변이를 검출 성공으로 계산하지 않는다. 기존 변이 생성 규칙과 옵션 생략 시 출력은 유지한다. [옵션·기록 형식·한계](../docs/mutate4go-reference-profile.md)에 상세 계약을 정리했다.

변경본의 중첩 모듈 6개 테스트 패키지와 상위 Go 모듈 15개 테스트 패키지가 통과했다. 독립 개발 명령 시험 2개도 5.117초에 통과했으며, 합성 프로젝트에서 후보 4개, killed 2개와 uncovered 2개, 기존 경로와 같은 후보 목록, 실제 기록 6개 및 원본 복구를 확인했다. 첫 독립 시험은 시험 환경의 Go 캐시 경로 누락으로 실패했다. 같은 환경의 직접 컴파일로 원인을 확인한 뒤 기존 고정 오프라인 실행 환경을 적용했으며 제품 코드는 바꾸지 않았다. 첫 실패 기록은 보존했다.

독립 코드 검토는 Approved/Critical 0/Important 0/Minor 0이다. 기존 v5 파일 중 이번 변경 대상 bridge 본문을 제외한 131개와 앞서 추가한 비교 실행기 5개 파일은 변하지 않았다. 중단된 초기 구현의 test-first 작성 순서는 확인할 수 없어 미확인으로 남겼고, 이후 재현한 오류 4건의 실패·수정 시험과 구분했다. 이 단계는 코드 검증 완료이며 새 설치물·실제 프로젝트의 상세 비교·운영 admission은 아니다.

## 전체 출력 전달과 설치본 검증

비교용 설치 구성을 support-v2로 명시적으로 선택하게 했다. 기본 support-v1은 기존 9파일 구성을 유지하고, 비교용 구성만 실행기 1개와 그 지문을 더 요구한다. 두 구성을 서로 대신 사용할 수 없으며, 기존 Go 명령의 생성된 실행 내용 4,592바이트와 SHA-256도 그대로다.

비교용 출력은 길이·내용 지문·이번 실행 식별값을 확인한 전체 바이트만 보관한다. 컨테이너 제거, 원본 입력 재검사, 중단 신호 처리기 복원이 끝나기 전에는 외부 소비자가 받지 못한다. 실행 중 생기는 파일은 별도 작업 복사본에 두고, 보호된 원본과 네 입력 폴더를 다시 검사한다. 이는 결과 전달의 완전성이지 내부 비교 보고서나 품질의 승인은 아니다.

새 전체 Python 시험 259개가 11.894초에 통과했고 독립 코드 검토도 Approved/Critical 0/Important 0/Minor 0이다. 같은 고정 빌더로 검증 환경에 오프라인 재설치한 뒤 15개 Python 파일이 소스와 같음을 확인했다. 소스 폴더가 없는 별도 위치에서 설치본으로 실행한 집중 시험 95개도 2.504초에 통과했다.

이후 고정한 Go 소스 144개 파일에서 빈 캐시로 두 번 빌드한 실행 파일 5개가 모두 같았다. 복사본과 최종 파일 목록도 그 지문에 맞는지 확인했다. 새 비교용 설치물은 10파일·31,890,535바이트이며 content SHA는 756cec437a5db349cc538b1645f7954cb71a75d41f93e5136bf697aa0ccd8096이다. 실제 설치본으로 이 구성의 입력 검사를 통과했다. 첫 준비는 증거 파일 두 개의 쓰기 권한 때문에 빌드 전에 거절됐고, 내용이 승인 지문과 같음을 확인한 뒤 해당 기록만 읽기 전용으로 바꾸었다. 검사나 소스는 완화하지 않았다. 이중 빌드·설치 입력 검증 뒤 수행한 실제 격리 비교는 아래에 기록한다.

## 같은 실제 프로젝트의 상세 대조

새 비교용 설치물로 go-multierror의 생산 코드 7개 파일 전체를 실행했다. 160.132초에 종료했고 원본 대조 2회, 변이 재실행 62회, 총 64개 실제 실행 기록을 받았다. 실행별 요청 식별값과 실행기 식별값은 각각 모두 달랐다. 원본 대조의 정적 테스트 목록은 24개이며, 과거 go-mutesting 기록은 이 개수를 숫자로 보고하지 않았으므로 같은 수를 보고했다고 소급하지 않는다.

두 도구의 원본 입력, 정적 테스트 목록 및 원본 대조 결과 지문은 모두 같았다. 변이 이후의 전체 입력 지문으로 실제로 같은 변경인지 대조하면 공통 13개가 있고, 이 13개의 결과도 모두 같았다. 나머지 후보를 같은 것으로 취급하지 않는다. 서로 다른 변이 규칙의 전체 후보 수가 29개와 33개이므로 검출 개수만으로 도구의 우열이나 점수 개선을 결론 내리지 않는다. 기본 도구와 고정 버전도 바꾸지 않았다.

새 33개 후보의 식별값·상태 순서는 이전 mutate4go v5 요약과 같았다. 이번에는 별도 새 실행에서 각 단계를 기록했다. 31개는 컴파일 성공 후 두 번씩 재실행했고 2개는 uncovered로 컴파일·재실행하지 않았다. multierror.go 110행의 1 → 0 변이는 두 번 모두 각각 30초 제한에 도달했으며, 그 다음 후보 5개도 끝까지 처리했다. 오류·시간 초과·미실행을 검출 성공에 합치지 않았다.

원문 보고서 62,921바이트와 빈 오류 출력을 보관했다. 원본 보호·출력 무결성, 외부 시간 초과·메모리 부족 없음, 정확한 컨테이너 제거와 최종 소유 컨테이너 0개를 확인했다. 저장된 원문을 다시 엄격하게 검사했고, 원문과 헤더를 합친 63,323바이트의 길이·지문이 실행 관측과 같았다. 완료 기록에 연결된 여섯 파일도 생성·감사 당시 지문과 같았다. 모든 원문은 비공개 임시 폴더에만 두었다.

이 결과는 공개 참조 한 프로젝트의 비교 관측이다. 독립적인 실제 기록 검토도 Approved/Critical 0/Important 0/Minor 0으로 완료했다. 검토 원문의 SHA-256은 c40393e0dc8fe723ffe9204e7e1fc2e03a90f5e5d0ab50a7d432405a5a14fc74이며, 검토자는 보관 자료를 다시 계산했지만 실제 프로젝트나 Docker를 재실행하지 않았다. 이 비교 단계에서는 새 artifact의 원래 Makefile이나 과거 실제 격리 실패 시험 10종을 재실행하지 않았다. 이후 원래 빌드는 다음 절에서 따로 검증했다. 같은 권한으로 실행되는 테스트 코드에 대해 기록 발급자를 인증하는 경계와 정식 운영 admission은 아직 남아 있으며 certified=false를 유지한다.

## 새 10파일 설치물의 원래 빌드 재검증

2026-09-10에 동일한 support-v2 설치물(content SHA 756cec437a5db349cc538b1645f7954cb71a75d41f93e5136bf697aa0ccd8096), 고정 SDK·의존성 및 go-multierror 전체 20파일로 인자 없는 원래 make를 실행했다. 원래 Makefile의 default → test → generate 관계를 유지했고 생성 단계 뒤 실제 패키지 테스트의 성공 출력을 확인했다. testrace나 대신 만든 빌드 명령을 실행한 것이 아니다.

첫 시도는 성공 관측을 만들기 전에 실패했다. 고정 image ID의 읽기 전용 조회는 No such image였고 소유 컨테이너는 0개였다. 같은 승인 digest를 별도 준비 작업으로 복구하고 이미지 지문·입력 없는 복구 실행을 확인한 다음, 변경 없는 driver와 입력으로 새 시도를 실행했다. 이미지가 없어진 원인은 확인하지 못했다. 첫 실패·명시적 복구·새 성공 기록을 각각 보존했으며, 실행 중 자동 다운로드나 버전 교체를 추가하지 않았다.

새 시도는 외부·원래 명령 종료 0, timeout·OOM 없음, 입력 보존과 컨테이너 제거를 기록했다. 원래 명령의 출력은 86바이트, 오류 출력은 0바이트였다. 출력 전체와 전달 헤더를 합친 457바이트의 지문은 1fd7939a2f04e887dd2b0fd8bfdd34752db72d5835476bacfde946d636849271이며, 완료 기록에 결합한 여섯 파일의 실제 지문도 일치했다. 완료 기록 자체의 SHA는 c7deeeca7f28dc04ea5c5f8afdd1ebfb853280c8a36b2bda2928ee784ba113b6이다. 관측 시간 72.973초는 실행 환경 준비부터 관측 저장까지이며 순수 테스트 시간이나 성능 비교값이 아니다. 종료 뒤 별도 조회에서도 소유 컨테이너 0개를 확인했다.

독립 실제 증거 검토는 Approved/Critical 0/Important 0/Minor 1, 최종 리뷰 SHA는 15b38fad7e6f1363330502d4a4611a5fa9da077d473fa56acab7d501131d6c1c다. Minor는 정적 리뷰의 중간본 지문을 최종본으로 인용한 기록 오류였다. 최종 인계에서 작업 범위 설명 문단만 달라졌음을 확인하고 인용과 정정 이력을 고쳤으며, 실제 실행 기록·제품 파일·원래 리뷰의 지적은 보존했다. 이 실제 빌드는 이전에 보관된 실행이며, 후속 문서 반영 때 다시 실행한 결과로 세지 않는다.

해당 checkpoint의 집중 시험 10개/52.199초와 전체 269개/12.959초는 통과했다. 첫 전체 시험은 로그 보호용 umask 077이 테스트에도 전달되어 기존 디렉터리 권한 fixture 하나가 실패했고, 그 기록은 보존했다. 실제 생성 권한을 대조한 뒤 로그는 보호하면서 테스트만 기존 022 환경에서 실행했다. 제품이나 테스트를 고친 것은 아니며 모든 umask 지원을 주장하지 않는다. 이 절은 정확한 설치물의 원래 빌드 관측만 증명한다. 그 뒤 수행한 같은 설치물의 격리 시험은 다음 절에 별도 기록한다. native 설치 연결·다른 언어·운영 admission·호스트 활성화는 여전히 미완료다.

SDK·설치물·의존성·원래 공개 프로젝트 입력 재검사와 마지막 별도 소유 컨테이너 조회도 통과했다. 문서 반영 직전 지문 대조는 새 실제 격리 실행으로 세지 않는다.

독립 실제 기록 검토는 PASS/Spec compliant/Approved, Critical 0/Important 0/Minor 0이다. 최종 검토 원문 SHA-256은 4bf9ca14fb99372b635505b1b625321d177fe6c54f71dfb6d4d992ef47231ba2이며 읽기 전용으로 보존했다. 실행 담당자는 모든 실행 세션의 종료 0을 직접 확인했지만, 세션 식별값·터미널 종료 응답 자체는 보관된 시험 파일만으로 독립 재확인할 수 없다는 검토 한계도 유지한다.

검증기 준비 과정에서는 OOM=true인데 외부 종료가 0인 유효한 관측을 잘못 거부하던 비공개 검증 조건 하나를 수정했다. 실패 재현과 수정 뒤 31개 시험, 독립 정적 재검토를 거쳐 위 실제 시험을 실행했다. 제품 코드는 바꾸지 않았다. 정적 검토의 별도 Minor 하나는 사용하지 않는 상수 이름이 내용 지문과 배포 지문을 혼동시키는 문제이며 실행 영향 없이 최종 정리에 남겨 뒀다. 실제 시험 기록 검토의 Minor 0과 같은 검토가 아니다.

증거 한계: CPU·프로세스 제한 횟수의 전후 숫자는 저장하지 않았으며 고정 비교 검사의 성공만 보관했다. 시간 초과·취소 시 시험 입력의 특정 명령 실행 여부를 추정하지 않는다. 전체 출력 전달·보관, 실행 관리자 자체의 임의 SIGKILL 강제 종료 뒤 복구, 통합 native 연결·운영 admission, 다른 언어와 실제 호스트 설치·활성화는 이 시험의 승인 범위가 아니다. 모든 결과는 probeOnly=true, certified=false다.

## 설치된 통합 명령의 Go 연결 검증

2026-09-10, 별도 자식 실행기나 관리 서버 없이 부모 SENTINEL 명령이 기존 GoSandbox를 직접 호출하도록 연결했다. 일반 실행 파일 묶음의 계약은 유지하고, Go 전용 데이터 형식 sentinel-go-oci-v1을 추가했다. 기본 check의 실행 거부와 전체 pass=false·certified=false는 바꾸지 않았다.

새 가상환경에 통합 실행기를 오프라인 설치한 뒤 Python 파일 16개가 현재 소스와 일치함을 확인했다. 설치된 sentinel install로 Go 묶음을 설치하고 소스 폴더 밖에서 명령을 실행했다. help·plan·doctor는 종료 0, 기본 check는 backendNotAdmitted/6이었으며 실행 세션은 생성되지 않았다.

대상은 위 go-multierror 1.1.1의 고정 20파일을 새 폴더에 복사하고 Go 검사 설정 한 파일을 추가한 입력이다. 생산 Go 파일 7개를 선택했으며, 작업 공간 설정까지 포함한 보호 대상은 22파일이다. SDK·도구·의존성은 이미 검증한 같은 설치물을 사용했고, 원래 언어 저장소나 애플리케이션 작업 폴더를 직접 검사하지 않았다.

|설치된 명령의 실제 실행|관측 결과|종료 후 확인|
|---|---|---|
|모듈 제한 300초로 검사 결과 수집|qualityFailed/2. 품질 미달을 통과나 실행 오류로 바꾸지 않음|프로젝트 22파일의 목록·내용·신원 일치, 소유 컨테이너 0개|

세 결과의 pass와 certified는 모두 false다. 공용 요약은 시간 초과와 다른 실행 기반 오류를 같은 backendError로 표현하므로, 80초 제한 관측에서 별도로 보관하지 않은 내부 상세 원인까지 주장하지 않는다. 취소는 실제 실행 연결이 살아 있을 때 전달했지만, 특정 변이 테스트가 시작된 시점까지 입증하는 시험은 아니다. 기존 전체 비교·원래 빌드·격리 10종을 이번에 다시 실행했다고 세지 않는다.

새 묶음 설정 지문은 4c53984256bd38c9164667ff10b82bc5c8cce0c4868e36e78d71922153bf5818, 설정을 포함한 새 검사 입력 목록 지문은 fb90415a5c1461674cb7d7f00138c3d4d726ec73927aa3bf3fc9d843f8602b0f다. 이전 20파일 입력과 새 21파일 입력을 같은 내용으로 표시하지 않는다.

연결부 독립 검토에서 입력 복사 중 취소가 일반 오류로 바뀌어 다음 모듈 준비가 계속되는 문제를 발견했다. 직접 취소와 실제 SIGINT 뒤 정리 오류를 각각 재현하고, 기존 취소 상태 처리를 재사용해 수정했다. 최종 독립 재검토의 남은 지적은 0건이다. 주 담당자가 새 집중 17개와 전체 297개 시험을 다시 실행해 통과를 확인했다. 전체 시험은 15.101초였으며, 단위 시험과 위 실제 실행을 구분한다.

## 다음 검증

1. 고정 공개 프로젝트의 실험용 통합 연결까지 확인했다. 다음은 실제 사용자 프로젝트의 지원 빌드 조합과 정식 운영 허용 조건을 검증한다. 공개 프로젝트 한 개의 결과를 모든 프로젝트 지원으로 확대하지 않는다. 새 관리 서비스나 서명 서비스를 불필요한 선행 조건으로 추가하지 않는다.
2. 동일 입력·테스트의 비교 관측과 믿을 수 있는 기록 발급자를 구분한다. 파일 지문이나 서명만 추가해 테스트 이벤트의 진위까지 보장한다고 표시하지 않는다. 전체 프로젝트 검사에서 부분 파일 목록을 허용하는 방법으로 비교를 편하게 만들지 않는다. 변이 규칙 수가 다른 두 도구의 점수도 단순 순위로 제시하지 않는다.
3. Java의 실제 Maven build와 Maven-aware 비교, 나머지 언어 도구 연결을 검증한다. Go의 설치·격리 승인으로 Java 등의 지원 상태를 승격하지 않는다.
4. 운영 admission, 즉 검증된 실행 조합을 정식 허용하는 조건을 충족한 뒤 동일 CLI를 호출하는 Codex·Claude Code plugin에 연결한다.
